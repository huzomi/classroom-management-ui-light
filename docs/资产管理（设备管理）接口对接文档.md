# 资产管理（设备管理）页面 — 接口对接文档

> 本文档用于指导另一个系统对接同一套资产管理（设备管理）后端接口，涵盖所有接口定义、数据结构、业务逻辑及注意事项。

---

## 一、页面功能概览

资产管理页面包含以下功能模块：

| 功能 | 说明 |
|------|------|
| **统计卡片** | 页面顶部展示 4 张统计卡片：设备总数、正常运行、异常/维修、即将报废，点击可筛选列表 |
| **设备列表** | 分页表格，支持按设备名称、设备类型、设备状态搜索 |
| **新增设备** | 弹窗表单新增设备，需要选择楼栋→楼层→教室（三级联动） |
| **编辑设备** | 弹窗表单编辑设备，编辑时多一个「设备状态」字段 |
| **查看详情** | 弹窗展示设备详情（只读） |
| **删除设备** | 单个删除（有确认弹窗） |
| **批量删除** | 多选后批量删除（有确认弹窗） |
| **导入/导出** | 预留了导入导出接口（当前前端尚未完全接入） |

## 三、接口详细说明

### 3.1 设备分页查询

- **URL**: `POST /equipment/page`
- **Content-Type**: `application/json`
- **请求参数**:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| page | number | 是 | 页码，从 1 开始 |
| pageSize | number | 是 | 每页条数，默认 10 |
| name | string | 否 | 设备名称（模糊搜索） |
| type | number | 否 | 设备类型编号 |
| status | number | 否 | 设备状态：0-正常，1-故障，2-报废 |
| scrap | number | 否 | 报废筛选：1-即将报废，2-正常，3-非正常 |

- **响应数据结构**:

```json
{
  "records": [
    {
      "id": "string",
      "name": "string",
      "brand": "string",
      "model": "string",
      "group": 1,
      "purchasingDate": "2024-01-01 00:00:00",
      "serviceLifeHour": 10000,
      "workingTime": 5000,
      "type": 1,
      "typeName": "投影仪",
      "status": 0,
      "buildingId": "string",
      "floorId": "string",
      "roomId": "string"
    }
  ],
  "total": 100,
  "size": 10,
  "current": 1,
  "pages": 10
}
```

- **⚠️ 注意**:
  - 前端框架 `useListPage` 通过 `fetchSetting` 配置 `listField: 'records'` 和 `totalField: 'total'` 来解析分页数据。
  - 前端传参名为 `pageNo`，但实际发给后端时转换为 `page`。
  - `scrap` 参数通过顶部统计卡片点击传入，`null` 表示不筛选（查全部），点击卡片时传入对应值。

---

### 3.2 设备详情

- **URL**: `GET /equipment/detail/{id}`
- **请求参数**: id 拼接在 URL 路径中
- **响应数据结构**:

```json
{
  "id": "string",
  "address": "XX楼栋-XX楼层-XX教室",
  "name": "string",
  "brand": "string",
  "model": "string",
  "group": 1,
  "purchasingDate": "2024-01-01 00:00:00",
  "serviceLifeHour": 10000,
  "workingTime": 5000,
  "type": 1,
  "status": "正常"
}
```

- **⚠️ 注意**:
  - 详情接口返回的 `status` 是**中文字符串**（如"正常"、"故障"、"报废"），不是数字。
  - 详情接口返回的 `address` 是拼接好的位置字符串，而列表接口返回的是 `buildingId`、`floorId`、`roomId` 三个 ID。

---

### 3.3 设备统计

- **URL**: `GET /equipment/count`
- **请求参数**: 无
- **响应数据结构**:

```json

  "totalCount": 100,

  "abnormalCount": 15,
  "scrapCount": 5
}
```

| 字段 | 说明 |
|------|------|
| totalCount | 设备总数 |
| normalCount | 正常运行设备数 |
| abnormalCount | 异常/维修设备数 |
| scrapCount | 即将报废设备数 |

## 五、业务逻辑与注意事项

### 5.1 三级联动选择（楼栋 → 楼层 → 教室）

新增/编辑设备时，位置选择采用**三级联动**：

1. **楼栋选择**：懒加载，首次展开下拉框时才请求 `/common/building/list`
2. **楼层选择**：选择楼栋后，自动请求 `/common/floor/list?buildingId=xxx`，同时清空楼层和教室已选值
3. **教室选择**：选择楼层后，自动请求 `/common/room/list?buildingId=xxx&floorId=xxx`，同时清空教室已选值
4. **编辑回显**：编辑时需要按照 `楼栋 → 楼层 → 教室` 的顺序依次加载数据，再回填值

### 5.2 统计卡片筛选

- 页面顶部 4 张卡片可点击，点击后高亮，并在分页查询时附带 `scrap` 参数
- 点击「设备总数」卡片时，传 `scrap = null`（即不传该参数），查询全部
- 点击「正常运行」卡片时，传 `scrap = 2`
- 点击「异常/维修」卡片时，传 `scrap = 3`
- 点击「即将报废」卡片时，传 `scrap = 1`

### 5.3 新增 vs 编辑的区别

- **新增**时：不显示「设备状态」字段，不需要传 `id` 和 `status`
- **编辑**时：显示「设备状态」字段，需要传 `id` 和 `status`
- 判断依据：表单中是否有 `id` 值（`ifShow: ({ values }) => !!values.id`）

### 5.4 详情接口与列表接口的差异

| 差异点 | 列表接口 | 详情接口 |
|--------|---------|---------|
| status 类型 | number (0/1/2) | string ("正常"/"故障"/"报废") |
| 位置信息 | buildingId, floorId, roomId | address (拼接好的字符串) |

### 5.5 删除/报废逻辑

- 当前前端的「删除」和「报废」功能使用的是同一个前端确认弹窗
- 实际后端接口为 `/equipment/del`，传 `{ ids: [...] }`
- 另有 `/edu/asset/scrap` 和 `/edu/asset/scrapBatch` 两个报废接口，但前端当前未实际调用后端（仅做了前端确认弹窗后直接回调）

### 5.6 导入/导出

- 导出接口 URL：`/edu/asset/exportXls`
- 导入接口 URL：`/edu/asset/importExcel`
- 当前前端导入导出按钮点击后仅弹出 `message.info('导入功能开发中...')`，尚未完全接入

### 5.7 分页参数映射

前端表格组件内部使用 `pageNo` 作为分页参数名，但在 `list` 函数中手动映射为 `page` 传给后端：

```
前端 pageNo → 后端 page
前端 pageSize → 后端 pageSize
```

### 5.8 列表数据解析配置

前端使用 `fetchSetting` 配置分页数据解析：

```
listField: 'records'   → 从响应中取 records 字段作为列表数据
totalField: 'total'     → 从响应中取 total 字段作为总条数
```

确保后端返回的分页数据包含 `records` 和 `total` 字段。
